    5. Chapter 4 - The Flutter client for the RdvMedecins application

    5.1. Architecture Overview

    This client communicates with the course’s [rdvmedecins-nestjs-server] server—which remains strictly unchanged—via the same routes (HTTP) already documented (POST, [/login], GET, [/getAllMedecins], GET [/getAllClients], GET [/getAgendaMedecinJour/:idMedecin/:jour], POST [/ajouterRv], POST [/supprimerRv]), with the same envelope JSON [{ status, data }] and the same token-based authentication [JWT] (header [Authorization: Bearer <jeton>]). For this variant, the overall architecture gains a third component: depending on the chosen compilation target (see Chapter 5), it is no longer just a browser that executes the client, but potentially a mobile or desktop operating system that directly executes the compiled code [Dart]—the server [NestJS], meanwhile, still only processes the same requests HTTP, regardless of the target.

    // =========================================================================
// main.dart
// -------------------------------------------------------------------------
// Entry point for the Flutter client. Equivalent to src/main.ts on the client side
// Vue.js from this course: this file explicitly starts the application
// (runApp(...) here; createApp(...).mount(...) on the Vue.js side) ET the
// configuration.
//
// Vue.js configures its application with app.provide(key, value), called
// directly on the application instance—Flutter/provider uses
// a widget, MultiProvider, placed at the root of the tree (see runApp(...)
// below): each ChangeNotifierProvider/Provider it contains makes
// makes the subtree it encloses available to TOUT, exactly
// just as app.provide(...) did for all descendant components—
// the same idea, expressed as a WIDGET rather than as a call to
// is an imperative method, because TOUT, in Flutter, is a widget (including
// the configuration of a shared state).
//
// The ORDRE construction still applies, for the same reasons as
// on the Vue.js side: AuthService(settings) requires that `settings` already exists
// (to read apiBaseUrl); RdvService requires authHttp ET from "settings."
//
// DIFFÉRENCE IMPORTANTE with Vue.js: createAuthStore(settings) and
// creerLanguageStore() on the Vue.js side read SYNCHRONEMENT localStorage
// during their construction, even before the first render. Their
// Flutter equivalents (AuthService.init(), TranslationsService.init())
// are ASYNCHRONES (see their respective files): main() itself must
// therefore become an async function, and ATTENDRE (await) these two
// initializations AVANT must call runApp(...)—otherwise, the first screen
// displayed would ignore any session or language already stored, the
// while shared_preferences responds.
//
// Like the Angular, React, and Vue.js clients in this course (single-page,
// no routing table), this Flutter client does not use QUE the
// minimal navigation provided by MaterialApp (required for showDialog(), see
// features/booking_dialog/booking_dialog.dart): AppRoot (see app.dart)
//displays either the login screen or the rest of the application, depending on
// AuthService.estConnecte—a simple Dart if/else statement is sufficient; a
// routing package (go_router or another) would not have added anything to a single-screen application
// with a single screen.
// =========================================================================

import 'package:flutter/material.dart';
import 'package:provider/provider.dart';

import 'app.dart';
import 'core/http/auth_http_client.dart';
import 'core/i18n/translations_service.dart';
import 'core/services/auth_service.dart';
import 'core/services/rdv_service.dart';
import 'core/services/settings_service.dart';

Future<void> main() async {
  // WidgetsFlutterBinding.ensureInitialized(): essential as soon as
  // calls a API Flutter AVANT runApp(...) (here, shared_preferences and
  // rootBundle.loadString(...) in TranslationsService.init()) - without
  // this line, these calls would fail on startup. Vue.js is in no way
  // comparable: the browser is always “ready” even before
  // src/main.ts runs.
  WidgetsFlutterBinding.ensureInitialized();

  // 1. SettingsService first: AuthService and RdvService depend on it
  // (apiBaseUrl).
  final settings = SettingsService();

  // 2. AuthService: receives settings directly from the manufacturer, such as
  // creerAuthStore (settingsStore) on the Vue.js side - then init() restores a
  // any cached session (see the header comment
  // above regarding the asynchronous nature of this step).
  final auth = AuthService(settings);
  await auth.init();

  // 3. the authenticated HTTP layer, then the business service—both
  // constructed ICI, just once, rather than inside a widget
  // (where they would be rebuilt with each render): exactly the same
  // principle as creerSettingsStore()/creerAuthStore(...), called a
  // only once before app.mount(...) on the Vue.js side.
  final authHttp = AuthHttpClient(auth);
  final rdv = RdvService(authHttp, settings);

  // 4. TranslationsService: loads the startup dictionary (the
  // stored language, or French by default) - AUCUNE dependency
  // order dependency with the previous steps (unlike
  // creerLanguageStore() on the Vue.js side, which had to wait
  // app.use(i18n): this file reimplements everything itself; see
  // core/i18n/translations_service.dart, so there is no
  // third-party plugin to install before you can use it).
  final translations = TranslationsService();
  await translations.init();

  runApp(
    // MultiProvider: combines multiple providers into a single widget,
    // rather than nesting them manually (Provider(...) > Provider(...)
    // > Provider(...) > ...)—resulting in readability comparable to the following
    // of calls like "app.provide(SettingsKey, ...); app.provide(AuthKey, ...);
    // app.provide(LanguageKey, ...);" on the Vue.js side, despite the difference in
    // form (a list of widgets rather than a sequence of instructions).
    MultiProvider(
      providers: [
        // .value(...) rather than Provider(create: ...): these instances
        // already exist (constructed above)—.value(...) simply makes them
        // simply available to the widget tree, without creating
        // new ones. ChangeNotifierProvider, specifically, subscribes
        // notifyListeners() and automatically redraws any
        // widget that has called context.watch<...>() on this provider (see
        // lib/app.dart) — the role played by the “reactive” nature of a
        // reactive(...) on the Vue.js side.
        ChangeNotifierProvider.value(value: settings),
        ChangeNotifierProvider.value(value: auth),
        ChangeNotifierProvider.value(value: translations),
        // RdvService is not PAS a ChangeNotifier (nothing in this service
        // does not change over time once it has been constructed): a simple Provider
        // is sufficient; it simply makes this instance available, without
        // any concept of notification.
        Provider.value(value: rdv),
      ],
      child: const RdvMedecinsApp(),
    ),
  );
}

    • line 60: [WidgetsFlutterBinding.ensureInitialized();] — required whenever you call a API, [Flutter], AVANT, or [runApp(...)] (here, [shared_preferences] and [rootBundle.loadString(...)])—without this line, these calls would fail at startup; [Vue.js] has nothing of the sort to anticipate, since the browser is always “ready” even before [src/main.ts] is executed.
    • Lines 70–71: [final auth = AuthService(settings); await auth.init();] — DIFFÉRENCE MAJEURE with [creerAuthStore(settingsStore)] on the side of [Vue.js], which reads [localStorage] SYNCHRONEMENT as soon as it is built: [AuthService.init()] is explicitly [async], and [main()] itself must therefore be the same in order to be able to ATTENDRE before [runApp(...)] — otherwise, the first screen displayed would ignore a session already stored in memory while waiting for [shared_preferences] to respond.
    • Line 89: [await translations.init();] — same note as above regarding the stored language; unlike [creerLanguageStore()] relative to [Vue.js], which had to wait for [app.use(i18n)], this step has no sequential dependency on the previous ones: [TranslationsService] reimplements everything on its own, without requiring any third-party plugins to be installed beforehand.
    • Lines 98–116: [MultiProvider(providers: [...], child: const RdvMedecinsApp())] — the equivalent, in the form of WIDGET rather than imperative calls, of the sequence [app.provide(SettingsKey, ...); app.provide(AuthKey, ...); app.provide(LanguageKey, ...);] on the [Vue.js] side: Each [ChangeNotifierProvider.value(...)] makes a pre-built instance available to the entire subtree.

class AppRoot extends StatefulWidget {
  const AppRoot({super.key});

  @override
  State<AppRoot> createState() => _AppRootState();
}

class _AppRootState extends State<AppRoot> {
  // --- application status ---------------------------------------------
  // the direct equivalent of the ref(...) fields in App.vue, in the form of simple
  // mutable fields from _AppRootState: setState(...) (see the methods
  // below) serves as a substitute for the automatic responsiveness of Vue.js.
  List<Medecin> _medecins = [];
  List<Client> _clients = [];
  AgendaMedecinJour? _agenda;
  String? _erreur;

  // saves the last search (doctor + day) so that
  // refresh the calendar after a booking or cancellation—even
  // regardless of whether it’s on the dernierIdMedecin/dernierJour side or the Vue.js side.
  int? _dernierIdMedecin;
  String? _dernierJour;

  // permanent reference to AuthService, to be able to
  // unsubscribe properly in `dispose()` (see below) — see the
  // comment on initState() below for the reason behind this choice.
  late final AuthService _auth;

  @override
  void initState() {
    super.initState();
    // context.read<AuthService>() : When initState() runs, the
    // widget is already correctly inserted into the tree (unlike the
    // constructor, where `context` is not yet usable for
    // dependency injection)—but we’re using PAS context.watch(...)
    // here: a StatefulWidget should subscribe to a provider only once
    // time, explicitly, and never inside initState() with watch()
    // (which assumes a build context). We therefore keep the reference in
    // a field (_auth) and subscribe ourselves using addListener(...).
    _auth = context.read<AuthService>();
    _auth.addListener(_onAuthChange);

    // equivalent to "watch(() => auth.estConnecte, ..., { immediate: true })"

    // callback, without waiting for the first change—useful if a session

// core/models/rdv_models.dart
// -------------------------------------------------------------------------
// Port of core/models/rdv.models.ts (the Vue.js client from this course),
// which is copied verbatim from the Angular and React clients: the Dart classes that
// describe the format of the data JSON received from the server NestJS. Like their
// counterparts TypeScript, these classes do not depend on any framework UI
// framework (no Flutter imports here)—it’s “pure” Dart, just like
// rdv.models.ts was "pure" TypeScript.
//
// DIFFÉRENCE STRUCTURELLE with TypeScript: a "interface" TypeScript is
// a simple description of FORME, verified only at compile time—
// at runtime, a decoded JSON object (JSON.parse) is used TEL QUEL,
// without conversion, and TypeScript “trusts” the developer (see
// "as Response<T>" from rdv.service.ts). Dart does not have this concept of typing
// implicit structural typing: jsonDecode(...) always returns
// dynamic types (Map<String, dynamic>, List<dynamic>...), which must be
// must be explicitly converted to Dart class instances using a constructor
// fromJson(...)—which is present in CHACUNE for the classes below. It’s more
// verbose to write once, but the conversion is verified at runtime
// (a missing key or one of the wrong type immediately raises an explicit exception
// ), whereas incorrect typing TypeScript might go unnoticed.
// =========================================================================

// -------------------------------------------------------------------------
// a common wrapper for all server responses (see Reponse<T> on the
// NestJS, and the client’s Reponse<T> interface Vue.js).
//
// Dart also generalizes using angle brackets (<T>), exactly like
// TypeScript—the main difference is that here, we cannot simply use
// an “as T” to convert the field [data]: you must provide the function
// that knows how to construct a T from raw JSON (the parameter
// [parseData] below), because Dart does not know T at runtime
// (type erasure prevents writing "T.fromJson(...)"
// directly).
// -------------------------------------------------------------------------
class Reponse<T> {
  final int status; // 0 = success, anything else = failure (see StatutReponse on the server side)
  final T? data;

  Reponse({required this.status, required this.data});

  factory Reponse.fromJson(
    Map<String, dynamic> json,
    T Function(dynamic donneesBrutes) parseData,
  ) {
    final donneesBrutes = json['data'];
    return Reponse<T>(
      status: json['status'] as int,
      data: donneesBrutes == null ? null : parseData(donneesBrutes),
    );
  }
}

      // the application, even if persistence fails (quota exceeded,
      // read-only storage...)—only a future restart of
      // the application would be affected (the user would have to log in again).
    }
  }

// whose get(...)/post(...) methods play exactly the same role—
// any code that wants to communicate with the server (here, only
// core/services/rdv_service.dart) calls the CES methods rather than the
// http package directly.
//
// Writing a class rather than a composable function is a natural choice
// in Dart/Flutter: unlike a <script setup> Vue.js (which
// runs only once per component instance; see the comment by
// auth.interceptor.ts), a ChangeNotifier or a Dart service class
// has no “body executed on every render” that you need to be wary of—
// so no equivalent of useCallback() is needed here either,
// but for a different reason: there simply isn’t a
// "function recreated on every render" to begin with, since the class is
// constructed only once by lib/main.dart (see below).
// =========================================================================

import 'dart:async' show unawaited;

import 'package:http/http.dart' as http;

import '../services/auth_service.dart';

class AuthHttpClient {
  final AuthService auth;
  final http.Client _client = http.Client();

  AuthHttpClient(this.auth);

  Future<http.Response> get(Uri url) => _envoyer(() => _client.get(url, headers: _entetes()));

  Future<http.Response> post(Uri url, {required Object body}) => _envoyer(
        () => _client.post(
          url,
          headers: {..._entetes(), 'Content-Type': 'application/json'},
          body: body,
        ),
      );

  // constructs the headers common to all protected requests—the equivalent
  // of the "new Headers(options.headers); if (auth.accessToken) {...}" on the
  // Vue.js, but in the form of a simple Map<String, String> (the type
  // expected by the http package, which is simpler here than a Headers class).
  Map<String, String> _entetes() {
    final accessToken = auth.accessToken;
    return accessToken == null ? {} : {'Authorization': 'Bearer $accessToken'};
  }

  // extracts what get(...) and post(...) have in common: executing the call
  // HTTP and then, if the response is 401, log the user out—the
  // function [appel] passed as a parameter acts as the "...options"
  // sent by `fetch(path, { ...options, headers: headers })` on the
  // Vue.js: at this point, it is not yet known whether this is a GET
  // or a POST; we just need to execute it and then examine its response.
  Future<http.Response> _envoyer(Future<http.Response> Function() appel) async {
    final reponse = await appel();
    //: A 401 error during a session means the token is no longer valid
    // (expired, or server restarted): the client is gracefully disconnected
    // rather than leaving the application in an inconsistent state (apparently connected
    // on the surface, but where no requests are successful anymore). We do not
    // an "await" on seDeconnecter(): the response HTTP (even if it’s an error)
    // must be returned to the caller without waiting for the local storage purge to finish
    // local storage, which completes on its own in the background.
    if (reponse.statusCode == 401) {
      unawaited(auth.seDeconnecter());
    }
    return reponse;
  }
}

// core/i18n/translations_service.dart
// -------------------------------------------------------------------------
// Porting FUSIONNÉ from src/i18n.ts (view-i18n configuration) ET from
// core/composables/language.composable.ts (Vue.js client from this course).
// Vue.js separates the two because vue-i18n, a third-party library already
// rich in features (pluralization, date/number formats...),
// handles all the actual translation work; language.composable.ts
// simply adds the ability to save the language selection in
// localStorage. Flutter does not have a direct equivalent to vue-i18n/react-
// i18next/@ngx-translate/core installed by default: rather than adding
// an additional dependency, this file reimplements in just a few
// lines—the subset used in this course: a
// dictionary with pointer keys ("LOGIN.TITLE") and a function t(key).
//
// DIFFÉRENCE DE PLATEFORME IMPORTANTE (see also the chapter “Porting
// the application to mobile, desktop, and web"): src/i18n.ts fetches
// each dictionary via a fetch("/i18n/{language}.json")—a URL
// relative URL, which assumes a SERVEUR WEB server serving the client files
// (Currently under development; a static server will be used once it is built). A
// Flutter mobile or desktop application has no PAS DE SERVEUR WEB to serve it
//: the code ET and its static resources (in this case, the files JSON) are
// EMBARQUÉS together in a single package installed on the device (.apk,
//.app, .exe...). This is why this file uses rootBundle.loadString(...)
// — the API Flutter component that reads a file specified in the [assets] section of
// pubspec.yaml directly from this package—rather than via a network call.
// On the web target, rootBundle relies behind the scenes on an actual request
// HTTP to the files published alongside the application, but this detail
// remains invisible here: the MÊME Dart code runs without any
// platform, across all three environments—which is precisely the central argument of
// this chapter.
// =========================================================================

import 'dart:convert';

import 'package:flutter/foundation.dart';
import 'package:flutter/services.dart' show rootBundle;
import 'package:shared_preferences/shared_preferences.dart';

const String _cleStockage = 'rdvmedecins.langue';
const String _langueParDefaut = 'fr';

class TranslationsService extends ChangeNotifier {
  String langueCourante = _langueParDefaut;

  // dictionaries that have already been loaded (avoids re-reading an asset file that has already been read
  // during the session)—same optimization as dictionnairesCharges on the
  // Vue.js (src/i18n.ts), but here the dictionary is stored directly
  // decoded rather than a simple Set of previously seen languages: Vue.js could
  // have been limited to a set because vue-i18n keeps LUI-MÊME the dictionaries
  // loaded into memory (setLocaleMessage); since there is no equivalent library
  // equivalent library here, this caching role must be handled directly by this
  // file.
  final Map<String, Map<String, dynamic>> _dictionnaires = {};

  // -----------------------------------------------------------------------
  // to be called UNE SEULE times, in lib/main.dart, AVANT runApp(...):
  // restores the language saved during a previous launch (if any
  // one) and loads its dictionary—equivalent to the end block of
  // creerLanguageStore() on the Vue.js side (reading langueMemorisee in
  // localStorage), but made explicitly asynchronous for the same
  // reasons already documented in core/services/auth_service.dart
  // (shared_preferences is asynchronous, unlike
  // localStorage).
  // -----------------------------------------------------------------------
  Future<void> init() async {
    String langueDepart = _langueParDefaut;
    try {
      final prefs = await SharedPreferences.getInstance();
      langueDepart = prefs.getString(_cleStockage) ?? _langueParDefaut;
    } catch (_) {
      // no readable preference: it starts in French, like
      // Vue.js (locale: 'fr' in createI18n({...})).
    }
    await _chargerDictionnaire(langueDepart);
    langueCourante = langueDepart;
    // No notifyListeners() here, for the same reason as in
    // AuthService.init(): this method is awaited before
    // runApp(...), so no widget is listening to this ChangeNotifier yet.
  }

  // -----------------------------------------------------------------------
  // equivalent to: changerLangue(language) on the Vue.js side (triggered by the
  // FR/EN buttons in lib/app.dart; see later in this chapter).
  // -----------------------------------------------------------------------
  Future<void> changerLangue(String langue) async {
    if (langue == langueCourante) {
      return;
    }
    await _chargerDictionnaire(langue);
    langueCourante = langue;
    notifyListeners(); // Here, however, the application is already running: a notification is indeed sent
    try {
      final prefs = await SharedPreferences.getInstance();
      await prefs.setString(_cleStockage, langue);
    } catch (_) {
      // the language change remains in effect for this execution even if
      // the save operation fails—only a future restart would be affected.
    }
  }

  // -----------------------------------------------------------------------
  // equivalent to: chargerDictionnaire(language) on the Vue.js side—even
  // caching principle (dictionnairesCharges), but reading an asset
  // embedded asset rather than a network fetch() (see the header of this file).
  // -----------------------------------------------------------------------
  Future<void> _chargerDictionnaire(String langue) async {
    if (_dictionnaires.containsKey(langue)) {
      return; // already loaded during a previous language change
    }
    final contenu = await rootBundle.loadString('assets/i18n/$langue.json');
    _dictionnaires[langue] = jsonDecode(contenu) as Map<String, dynamic>;
  }

  // -----------------------------------------------------------------------
  // the translation function itself—called t('LOGIN.TITLE') from
  // the widgets (see lib/features/...), exactly like t('LOGIN.TITLE')
  // on the Vue.js side (useI18n().t). The key is "separated by a dot" (a dot separates
  // each level): we therefore descend through the nested dictionary JSON one
  // segment at a time, rather than flattening the dictionary once and for all
  // for all of them, as vue-i18n does internally—a choice that remains
  // more than sufficient for the size of these two dictionaries.
  // -----------------------------------------------------------------------
  String t(String cle) {
    final dictionnaire = _dictionnaires[langueCourante];
    if (dictionnaire == null) {
      return cle; // Dictionary not yet loaded: display the key itself as a last resort
    }
    dynamic valeurCourante = dictionnaire;
    for (final segment in cle.split('.')) {
      if (valeurCourante is Map<String, dynamic> && valeurCourante.containsKey(segment)) {
        valeurCourante = valeurCourante[segment];
      } else {
        return cle; // key not found: same fallback as above
      }
    }
    return valeurCourante is String ? valeurCourante : cle;
  }
}

// Porting src/app/features/booking-dialog/BookingDialog.vue (client

//
// DIFFÉRENCE STRUCTURELLE IMPORTANTE with Vue.js (and with the other three
// widgets from lib/features/): BookingDialog.vue is a component of TOUJOURS
// PRÉSENT in the tree, whose prop [ouvert] (a Boolean held by
// App.vue) controls the display (v-if="open")—EXACTEMENT the same
// choice as the Angular and React clients in this course, driven by the need
// to prevent Vue.js and Bootstrap’s JavaScript from competing for the
// same information (“Is the modal open?”).
//
// Flutter doesn’t have this problem: a dialog is NOT a widget
// that is conditionally shown or hidden in the tree, but a VRAIE
// PAGE, pushed onto the navigation stack (the Navigator) the moment
// it is opened, along with showDialog(...)—and automatically popped off the stack upon
// closing. Therefore, there is no NI “open: bool” state to maintain in the
// parent widget (see lib/app.dart, which has no field equivalent to
// creneauEnReservation on the Vue.js side), NI “confirm”/“close” events to
// send: showDialog(...) returns a Future that resolves with the
// value passed to Navigator.pop(...)—null if the user closed
// without making a selection; otherwise, the ID of the selected patient. This is the widget
// APPELANT (lib/app.dart) that waits for this Future using `await` to determine what
// to do next—a complete reversal of the direction of communication by
// compared to the two Vue.js events.
// =========================================================================

import 'package:provider/provider.dart';

// selected patient (or null if the user canceled or closed without making a selection).
// This is the function that lib/app.dart calls—never call the
// the constructor of _BookingDialogContent below.
// -----------------------------------------------------------------------

  required BuildContext context,
  required CreneauJson creneau,
  required List<Client> clients,
}) {

    context: context,

}

      return;

    // passes idClient as the result of the Future returned by
    // ouvrirBookingDialog(...) — the equivalent, in a single call, of
    // emit('confirm', { idClient }) SUIVI for the closure (implicit,
